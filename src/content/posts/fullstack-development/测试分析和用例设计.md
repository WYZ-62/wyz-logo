# 测试分析和用例设计

这份课程笔记的主线非常明确：先定义测试用例是什么，再讲几种最常见的设计方法，随后补上高质量测试用例的评价标准，以及开发排障中常见的问题定位思路。  
如果按学习逻辑重组，它更适合作为一篇“怎样把测试从凭感觉点点点，变成结构化设计”的入门与复习文章。

## 一、先理解测试用例到底是什么

课程一开始给出的定义很清楚：

测试用例是为了验证特定需求而设计的完整测试单元，通常包含：

- 前置条件
- 输入
- 执行步骤
- 预期结果

### 1. 可选项

课程里还提到一些常见辅助字段：

- 编号
- 优先级
- 标题

这些字段不是绝对必须，但对团队协作很有帮助。

### 2. 五个核心要素

课程特别强调了不可缺失的五项内容：

- 测试环境
- 操作步骤
- 测试数据
- 预期结果
- 实际结果

如果缺了这些，用例往往会变成：

- 无法复现
- 无法判断
- 无法维护

## 二、等价类划分：先把无限输入压缩成有代表性的几类

这是课程里讲的第一种基础方法。

### 1. 核心思想

把输入按特征分为若干类别，每类内部可以认为是等价的，不必每一个值都测。

### 2. 常见分类

课程中提到：

- 有效等价类：符合需求的合理输入
- 无效等价类：违反约束的异常输入
- 可能还会区分是否存在边界关联

### 3. 为什么它有价值

因为它能在不牺牲覆盖意图的前提下：

- 显著减少测试数量
- 提升测试效率
- 为后续边界值分析打下基础

等价类划分本质上是在解决“测试不可能穷举”这个现实问题。

## 三、边界值分析：很多 Bug 不在中间，而在边缘

课程接着讲边界值分析，这通常和等价类配合使用。

### 1. 核心思想

围绕输入/输出的临界点和次边界设计测试。

### 2. 课程里强调的几个点

- 边界值通常取等价类边界点
- 也要取边界两侧的值
- 需要覆盖正常、边界、次边界、越界等场景

比如限制长度 `6~200` 时，测试点可能包括：

- 6
- 7
- 199
- 200
- 201

### 3. 为什么它重要

因为很多问题不是在“正常值”上暴露，而是在：

- 多一位
- 少一位
- 临界刚好相等

这些边缘点上暴露。

## 四、场景分析法：测试不只测字段，还要测流程

课程中的场景分析法，是把测试从“字段级判断”推向“流程级验证”的关键一步。

### 1. 核心思想

基于用户真实使用路径设计测试用例。

### 2. 典型组成

课程里提到：

- 基本流：主流程
- 备选流：异常、分支、替代路径

例如类似 ATM 取款的场景，会涉及：

- 插卡
- 输密码
- 取款
- 退卡

同时还要考虑：

- 输错密码
- 余额不足
- 设备故障

### 3. 为什么它不可替代

因为等价类和边界值更偏输入维度，  
而场景分析法真正关注的是：

- 用户能不能走完整个流程
- 系统在异常分支下会怎么表现

## 五、错误推测法：经验不是方法的替代，但能补方法的盲区

课程里把错误推测法定义为：

- 依据测试人员经验与直觉
- 针对程序脆弱点和典型异常输入
- 去设计额外用例的方法

### 1. 它通常关注哪些地方

课程列出了一些典型方向：

- 用户注册重复
- 查询不存在订单
- 参数遗漏或格式错误
- 系统鲁棒性与提示准确性

### 2. 它的价值

主要在于：

- 补齐结构化方法未覆盖到的风险点
- 提升对隐性 Bug 的发现能力

### 3. 它的局限

课程也强调：

- 不能完全替代系统化方法
- 最好建立在等价类、边界值、场景法之上

这说明经验很重要，但经验更适合做“补刀”，而不是当唯一方法。

## 六、高质量测试用例，至少要满足这几条标准

课程里专门给出了高质量测试用例的评价标准，这非常值得直接保留。

主要包括：

- 表达清晰无歧义
- 操作性强
- 输入输出明确
- 可维护性好
- 需求覆盖率高
- 缺陷检出能力强

这几个标准其实分别对应了不同阶段的使用价值：

- 写的时候不容易误解
- 执行的时候不容易走偏
- 维护的时候不容易崩掉
- 上线前真正能帮你发现问题

## 七、测试分析不仅用于写用例，也常常直接服务于问题排查

课程后半段开始出现一些偏工程诊断的内容，比如：

- JDK 自带问题排查工具
- 操作系统辅助命令
- IDE 远程调试
- 第三方诊断工具
- Maven 依赖与构建失败排查
- 日志输出异常排查
- Java 进程启动失败与卡顿排查

这说明测试分析能力和问题定位能力，其实是连在一起的。

### 1. 常见排查工具

课程中提到：

- JDK 工具：`jps`、`jmap`、`jstack`、`jstat`
- 系统命令：`ps`、`top`、`netstat`、`grep`、`iostat`
- 第三方工具：Arthas、MAT、JProfiler

这些工具的价值，在于帮助定位：

- 进程状态
- 内存问题
- 线程问题
- GC 行为
- 启动失败与卡顿

### 2. 构建与日志问题

课程还单独讲了：

- Maven 依赖坐标三要素：`groupId / artifactId / version`
- 日志门面、日志实现、配置三者要匹配

这些内容虽然看似偏开发，但和测试执行、环境排查是强相关的。

## 八、把这份笔记压缩成一条适合复习的主线

如果只保留最核心的学习顺序，这篇《测试分析和用例设计》可以压缩成下面这条链：

1. 先理解测试用例的基本结构和五个核心要素
2. 用等价类划分减少输入组合数量
3. 用边界值分析覆盖最容易出问题的临界点
4. 用场景分析法覆盖真实业务流程和异常分支
5. 用错误推测法补齐隐性风险点
6. 再用高质量标准反过来检查用例本身写得够不够好
7. 最后把测试分析延伸到构建、日志、进程和运行时问题排查

## 九、这份课最重要的心法

课程真正想说明的，不是“测试方法名很多”，而是：

**测试设计的本质，是用有限的用例，最大化覆盖真实风险。**

真正有效的测试，不是把路径都点一遍，而是：

- 知道哪些输入可以合并
- 知道哪些边界一定要测
- 知道哪些流程不能漏
- 知道哪些历史事故最容易重演

当这些都具备以后，测试就不再只是执行动作，而会变成对需求、实现和风险的结构化理解能力。
