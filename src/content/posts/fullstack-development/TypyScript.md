# TypyScript

这份课程笔记的核心非常明确：先说明为什么 JavaScript 的动态类型会带来运行时风险，再引出 TypeScript 的静态类型检查优势，随后逐步进入基础类型、数组与元组、`enum / void / never`、`null / undefined`、`any / unknown`，最后落到 `interface` 与 `type` 的区别。  
如果按学习逻辑重组，它更适合作为一篇“TypeScript 为什么值得学，以及最基础的类型规则该怎么理解”的入门与复习文章。

## 一、TypeScript 为什么会出现：不是为了变复杂，而是为了把错误提前

课程一开始先对比了 JavaScript 动态类型的风险。

### 1. JavaScript 动态类型的问题

动态类型的主要麻烦在于：

- 很多错误要等到运行时才暴露
- 容易在大型项目里埋下隐患
- 出错后定位成本较高

### 2. TypeScript 的核心优势

课程里总结得很直接：

- 在编译阶段做静态类型检查
- 更早发现类型错误
- 100% 兼容 JavaScript 语法

这意味着 TypeScript 的价值，不是替代 JavaScript，而是在不放弃 JS 生态的前提下，引入更强的类型约束。

## 二、最基础的一步：先学会显式声明类型

课程里先讲的是类型声明本身。

你可以通过：

- `let`
- `const`
- `type`

这样的语法明确告诉系统变量、参数或结构应该属于什么类型。

它最直接的好处包括：

- 变量用途更清楚
- 类型不匹配能更早报错
- 为函数、接口、对象结构打下基础

课程里强调的一点很重要：

**类型检查发生在编译阶段，不影响最终 JavaScript 运行方式。**

## 三、数组和元组看起来像一类数据，实际上约束强度完全不同

课程里对数组类型和元组类型做了对比，这一段很值得保留。

### 1. 数组类型

数组表示：

- 元素类型统一
- 长度可动态变化

例如：

- `string[]`
- `Array<number>`

它支持：

- `push`
- `pop`

以及其他数组方法，灵活性更强。

### 2. 元组类型

元组表示：

- 固定长度
- 每个位置的类型事先确定

例如：

- `[string, number]`

### 3. 什么时候该用谁

课程里给出的意思可以总结成：

- 结构化小数据，用元组更清晰
- 同质大规模集合，用数组更合理

这体现的本质不是语法差异，而是建模精度不同。

## 四、`enum`、`void`、`never` 这几个类型，都是为表达“意图”服务的

### 1. `enum`

课程里对枚举的解释很清楚：

- 用于表示一组命名常量
- 默认可以自动编号
- 也支持手动赋值

它的价值在于：

- 提高可读性
- 减少魔法数字
- 更适合表达有限状态集合

### 2. `void`

`void` 用来表示：

- 函数没有返回值

课程里还特别提醒：

- 它不是 `undefined` 的别名
- 使用时不应该 `return` 具体值

### 3. `never`

`never` 表示：

- 理论上不可能到达的类型

课程里提到它常见于：

- 抛出异常的函数
- 永远不会正常结束的代码路径

它的作用其实很重要，因为它能帮助系统理解：

- 某些分支绝不会产生有效返回
- 有助于更严格的穷尽检查

## 五、严格模式下，`null` 和 `undefined` 不能再被随便忽略

课程专门讲了严格模式下的 `null / undefined` 类型行为，这部分非常关键。

### 1. 在严格模式下会发生什么

当开启严格空值检查时：

- `null`
- `undefined`

不再能随意赋值给任意类型。

### 2. 为什么这样更安全

课程里给出的设计意图很明确：

- 强制开发者显式处理空值
- 避免很多运行时空引用问题

### 3. 一个重要的工程含义

这说明 TypeScript 并不是单纯给代码加注释，而是在推动：

**把“可能为空”这件事显式写进类型系统。**

## 六、`object`、`type` 和结构化建模：越往后写，越能看出类型设计能力

课程里提到 `object` 类型的局限：

- 它只说明“这是个对象”
- 但并不能提供足够清晰的结构约束

这就是为什么课程会更推荐用：

- `type`
- 或 `interface`

来定义对象结构。

### 1. `type` 的优势

课程里强调：

- 能定义更清晰的对象结构
- 支持交叉类型、联合类型等表达
- 更适合复杂业务建模

这意味着在真实项目里，如果只写 `object`，往往类型信息是不够的。

## 七、`any` 和 `unknown` 的差别，代表的是“放弃检查”还是“先不确定”

课程把 `any` 和 `unknown` 放在一起讲，这非常有代表性。

### 1. `any`

课程里对 `any` 的定位很直接：

- 关闭类型检查
- 几乎允许任意操作

它适合：

- 临时开发
- 代码迁移

但代价也很明显：

- 会失去类型系统保护

### 2. `unknown`

`unknown` 被课程定义为：

- 更安全的替代方案

因为它要求你先做判断，比如：

- `typeof`
- `instanceof`
- 其他类型守卫

才能继续访问或使用值。

### 3. 使用原则

课程里给出的建议很实用：

- `unknown` 更适合作为 `any` 的默认替代
- 断言只在你真的有更高把握时使用
- 非空断言要谨慎，因为它可能重新引入运行时风险

## 八、类型断言不是“让类型变对”，而是“告诉编译器你更清楚”

课程里提到了三种常见写法：

- 尖括号语法
- `as` 语法
- 非空断言 `!`

其中更推荐的是：

- `as`

因为：

- 在 React / JSX 中更兼容
- 可读性更稳定

但课程也提醒得很明确：

- 断言不是类型转换
- 它只是告诉编译器“我知道自己在干什么”

所以过度断言，本质上是在把风险从编译期重新推回运行时。

## 九、`interface` 和 `type` 怎么选，不是二选一，而是场景侧重点不同

课程最后讲了 `interface` 与 `type` 的核心区别，这部分在真实项目里非常常用。

### 1. `interface` 的特点

课程提到：

- 支持重复声明并自动合并
- 继承方式通常通过 `extends`
- 更适合描述对象类型

### 2. `type` 的特点

课程提到：

- 重复定义会报错
- 更适合表达别名、联合、交叉等复杂组合
- 更偏“类型表达能力”

### 3. 怎么理解这种差异

可以简单记成：

- 描述对象结构时，`interface` 往往更自然
- 做复杂类型组合时，`type` 更灵活

这不是互相取代，而是建模工具箱里的两种不同工具。

## 十、把这份笔记压缩成一条适合复习的主线

如果只保留最核心的学习顺序，这篇 TypeScript 笔记可以压缩成下面这条链：

1. 先理解 TypeScript 是为了解决 JavaScript 运行时类型风险
2. 学会基础类型声明和静态检查机制
3. 再区分数组与元组这两种不同精度的数据建模方式
4. 理解 `enum / void / never` 各自表达的语义意图
5. 在严格模式下正确处理 `null / undefined`
6. 尽量避免泛化的 `object`，用 `type / interface` 描述结构
7. 理解 `any` 与 `unknown` 的安全边界
8. 把断言当作谨慎使用的补充工具
9. 最后掌握 `interface` 与 `type` 的使用侧重点

## 十一、这份课最重要的心法

课程真正想说明的，并不是“TypeScript 语法很多”，而是：

**TypeScript 的价值在于把本来靠经验和约定维持的代码边界，提前写进类型系统。**

当你理解了：

- 哪些值可能为空
- 哪些结构必须固定
- 哪些地方应该保守处理而不是图省事
- 哪些地方该用 `type`，哪些地方该用 `interface`

你就会发现 TypeScript 并不是让开发更慢，而是在帮助你把很多运行时问题，前移到写代码的那一刻。
