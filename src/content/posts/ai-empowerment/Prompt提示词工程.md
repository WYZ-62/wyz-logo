# Prompt提示词工程

这份课程笔记的重点非常集中：它不是泛泛讲“怎么和 AI 对话”，而是直接把 Prompt 当成一种工程化输入设计能力，核心主线围绕 `3C` 框架、Few-shot 示例、风格对齐和结构化输出展开。  
如果按学习逻辑重组，它更适合作为一篇“怎么把提示词从随手一问，变成可复用输入协议”的实践文章。

## 一、Prompt 工程真正解决的，不是“会不会问”，而是“能不能稳定复现”

很多人第一次用大模型时，会把 Prompt 理解成“把需求说出来”。  
但课程里的思路更进一步：

**Prompt 工程的核心，不是让模型偶尔答对，而是让模型更稳定、更接近预期地输出。**

这也是为什么课程从一开始就给出了一个非常实用的框架：`3C`。

## 二、3C 框架：让 Prompt 从一句话变成结构化任务描述

课程里把提示词拆成三个部分：

- `Context`
- `Command`
- `Constraint`

这三个部分加起来，基本就构成了一个可执行的任务输入协议。

### 1. Context：在什么情境下

Context 用来告诉模型：

- 背景是什么
- 你是谁
- 当前任务发生在什么环境里

课程中的示例很直观，比如：

- 你是一位资深科技记者，正在撰写一篇关于人工智能的深度报道
- 你是一名大学生，正在准备一次课堂演讲

这部分的作用，不是“增加文采”，而是缩小模型的理解空间，让它更快进入正确角色和语境。

课程里还强调了两个小原则：

- 提供真实、具体的信息，比如角色、领域、目标
- 避免模糊表达，比如“有关这个话题……”

### 2. Command：请完成什么

Command 是任务指令本体，回答的是：

**你到底要模型做什么。**

课程里给出的常见动作包括：

- 写作
- 分析
- 总结
- 翻译
- 对比
- 生成
- 解释
- 列出
- 设计

这一部分最重要的原则是：

- 动作明确
- 尽量避免歧义

比如：

- “请用通俗易懂的语言解释量子计算的基本原理”
- “请为这篇论文写一个 500 字摘要”

模型不是不会做，而是怕你没有把动作说清楚。

### 3. Constraint：要按什么边界输出

Constraint 的作用，是控制输出形式、长度、风格和内容要求。

课程里给出了几类典型约束：

- 格式：列表、分点、表格等
- 长度：比如“不超过 200 字”
- 风格：比如“语气正式”“口语化”
- 内容要求：比如“至少包含 3 个例子”“避免使用专业术语”

这部分特别关键，因为没有约束的模型输出，通常“能看”，但不一定“能用”。

## 三、3C 框架真正厉害的地方，是把模糊提问变成了可复用模板

课程里有一段很重要的总结可以转化成一句口诀：

**上下文定场景，指令定动作，约束定标准。**

这句话很适合作为 Prompt 工程的记忆锚点。  
因为你之后无论做总结、抽取、写作还是代码生成，几乎都能沿着这条线组织输入。

## 四、Few-shot 的核心价值：不是给模型看例子，而是给它看“你想要的风格”

课程后半段开始进入更实战的部分，其中最有价值的一块就是 Few-shot。

### 1. 什么是 Few-shot

简单理解就是：

- 先给模型一个或几个示例
- 再让它按照示例继续完成任务

### 2. Few-shot 为什么重要

课程里通过 Java 代码示例讲了一件很现实的事：

即便你已经写了 Prompt，AI 生成的代码也未必像你团队写出来的代码。

比如团队会有这些隐含规范：

- 异常统一用 `BusinessException`
- 使用特定注解风格
- 日志格式统一
- 方法结构有固定写法

如果只写口头要求，模型可能“知道方向”，但仍然会在细节上跑偏。  
这时直接给一段团队已有代码，效果通常会明显更稳定。

### 3. Few-shot 的本质

它不是让模型背答案，而是让模型学习：

- 风格
- 结构
- 习惯
- 取舍

课程里对这一点的总结可以提炼成一句话：

**让 AI 写出“像你写的”代码，而不是“能跑但不像团队风格的”代码。**

## 五、为什么团队代码规范最好不要只写在嘴上

课程在 Few-shot 示例后，其实表达了一个更偏工程化的观点：

你可以先用 3C 框架告诉模型“做什么”，  
但如果你还想让输出更像团队真正的产物，就应该进一步提供：

- 示例代码
- 风格样板
- 结构模板

这说明 Prompt 工程真正成熟的状态，不是一次次临时发挥，而是把“团队经验”变成 AI 可以复用的输入资产。

## 六、结构化 Prompt 的目标，是让 AI 输出能直接接流程

课程里没有只停留在“提高可读性”，而是强调了 Prompt 的工程价值。

真正好的 Prompt 往往具备这些特征：

- 任务结构清楚
- 输出标准明确
- 可以复用
- 可以和系统流程对接

这也是为什么：

- `Context` 负责减少理解偏差
- `Command` 负责减少任务歧义
- `Constraint` 负责减少结果波动

Prompt 工程，本质上是在减少模型自由发挥带来的不确定性。

## 七、Prompt 工程不是模型技巧，而是输入设计能力

把这门课再压缩一下，它真正想训练的不是“会不会写几句提示词”，而是下面这件事：

**你能不能把一个任务，设计成模型容易理解、容易执行、容易稳定复现的输入结构。**

这和传统软件工程里做接口设计，其实很像。

- 你要定义上下文
- 你要定义动作
- 你要定义约束
- 你要定义样例

只不过这次对接的对象，从程序换成了模型。

## 八、把这份笔记压缩成一条最实用的学习主线

如果只保留最核心的学习顺序，这篇 Prompt 提示词工程笔记可以压缩成下面这条链：

1. 先接受 Prompt 工程追求的是稳定输出，不是偶然答对
2. 用 `Context / Command / Constraint` 搭出任务骨架
3. 让模型先知道场景，再知道动作，再知道标准
4. 当需要风格一致时，引入 Few-shot 示例
5. 当需要团队规范一致时，直接提供真实样板代码或模板
6. 最后把 Prompt 从“自然语言”升级成“可复用输入协议”

## 九、这份课最重要的心法

课程真正想告诉你的，不是“Prompt 有很多技巧”，而是：

**Prompt 本质上是一种任务设计能力。**

说得更具体一点：

- 没有上下文，模型容易误解场景
- 没有明确指令，模型容易偏离动作
- 没有约束，模型容易输出失控
- 没有示例，模型很难真正学到你的风格

当你把这些都补齐后，Prompt 就不再是“问 AI 的一句话”，而会变成你和模型协作时最关键的输入接口。
