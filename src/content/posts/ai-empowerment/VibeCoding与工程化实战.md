# VibeCoding与工程化实战

这份课程笔记的重点不是“AI 会不会写代码”，而是怎样把 AI 编码从零散试用，升级成一套可复用、可验证、可落地的工程流程。它先从 Claude Code CLI 和 MCP 接入讲起，再进入 Skill 机制，最后通过一个团队任务管理工具的例子，把 VibeCoding 这套工作方式跑通。  
如果按学习逻辑重组，它更适合作为一篇“如何让 AI 真正进入工程协作，而不是只停留在演示效果”的实践文章。

## 一、VibeCoding 不是随便让 AI 写代码，而是把需求、上下文和规范一起喂给它

课程里给出的 VibeCoding 流程可以概括成一句话：

**描述需求 -> Claude Code 自动生成 -> 审查与调试**

但课程同时也强调，这个流程成立有两个重要前提：

- AI 要能看见真实世界
- AI 要知道团队规范

而这正对应了两类能力：

- `MCP`：补上下文与真实数据
- `Skill`：补团队约束与操作模板

换句话说，VibeCoding 不是一句更酷的口号，而是：

- 让 AI 既有“看见现实”的能力
- 也有“按团队规则做事”的能力

## 二、Claude Code CLI 是进入工程化 AI 编码的入口

课程前半段先讲了 `Claude Code CLI` 的安装和使用，这部分更多是在搭环境，但也有几个值得保留的要点。

### 1. 最基础的环境要求

课程里明确提到：

- 需要 `Node.js 18+`
- 可以用 `npm` 全局安装 Claude Code

这说明 Claude Code 进入工程环境的方式，本质上更像一个终端开发助手，而不是网页聊天工具。

### 2. 登录与模型接入

课程还讲了：

- 可以登录 Claude 账号
- 也可以通过兼容 Anthropic API 的国内模型接入，比如通义千问兼容接口

这里最重要的不是某个具体服务名，而是理解：

**Claude Code 这类工具的关键不只在模型本身，还在它能否进入本地项目、终端和工具链。**

### 3. 常用命令与问题排查

课程里列出了多组命令，比如：

- 会话内命令：帮助、清屏、切模型、查看状态等
- Shell 启动命令
- 常见问题排查：`command not found`、权限不足、Node 版本过低、网络超时

这部分说明一个很现实的事实：

AI 编码工具首先也是开发工具，工具本身的安装和可用性，是后面所有工程实践的前提。

## 三、为什么“只有 AI”还不够：它看不见真实环境，也不理解团队习惯

课程中段有一组截图专门讲“大语言模型的局限”，这一段很关键。

总结起来，AI 单独写代码常见的三个问题是：

### 1. 无法访问实时数据

比如：

- 不能直接查询数据库当前结构
- 不知道线上真实表长什么样

### 2. 无法执行操作

比如：

- 不能自己执行 SQL
- 不能直接访问你的 API、文件系统或工具输出

### 3. 无法感知团队上下文

比如：

- 不知道团队命名习惯
- 不知道日志格式
- 不知道异常处理规范
- 不知道返回结构约定

课程里这部分其实在回答一个很核心的问题：

**为什么 AI 经常能写出“看起来对、但放不进项目里”的代码。**

答案不是模型不努力，而是它缺少：

- 真实环境上下文
- 团队约束上下文

## 四、MCP 解决的是“让 AI 看见世界”

课程对 `MCP` 的解释非常形象：  
它就像 AI 世界的 “USB-C 接口”，统一了模型和外部工具、外部资源之间的连接方式。

### 1. MCP 是什么

`MCP`（Model Context Protocol）是 Anthropic 推出的开放协议，用于定义 AI 模型与外部工具和数据源之间的标准通信方式。

课程的比喻非常适合记忆：

- 在 USB-C 统一接口之前，不同设备接口各不相同
- MCP 想做的，就是把 AI 接外部世界的方式标准化

### 2. MCP 的基本架构

课程里给出的链路可以概括为：

- Host：比如 Claude Code
- Client：MCP 客户端能力
- Server：真正连接外部资源的 MCP Server
- External Resources：数据库、API、文件系统等

### 3. MCP 解决了什么

课程给出的表格很有代表性：

没有 MCP 时：

- AI 只能猜表结构
- 只能猜 API
- 只能猜文件内容

有 MCP 时：

- AI 能读取数据库并执行 SQL
- AI 能调用 API 看真实结果
- AI 能查看本地或远程文件

### 4. MCP 的三类典型能力

课程中提到：

- `Tools`：工具调用
- `Resources`：资源读取
- `Prompts`：提示模板

最值得记住的是：  
MCP 不是让模型变强，而是让模型获得现实世界输入和执行通道。

## 五、MySQL MCP Server：一个非常典型的工程化上下文入口

课程后半段用 `MySQL MCP Server` 做了实操，这一步很有代表性。

### 1. 安装逻辑

课程强调了一点：

MCP Server 本质上是一个独立运行的程序，通过标准输入输出和 Claude Code 通信。

安装它通常要告诉系统两件事：

- 这个 Server 怎么启动
- 它要连接哪个外部资源

### 2. 环境前置条件

课程里提到的准备包括：

- Node.js
- Claude Code
- MySQL 可访问环境

### 3. 配置方式

课程展示了几种常见接入方式：

- 命令行直接添加
- 在配置文件中声明 `mcpServers`
- 用 `npm` 方式安装 Server

这说明 MCP 不只是“有个概念”，而是可以非常具体地把数据库能力挂进 AI 编码流里。

### 4. 它在工程里的真正意义

当 Claude Code 能通过 MCP 读取数据库结构时，就意味着：

- 生成表结构相关代码时不再纯靠猜
- 字段、索引、表名会更接近真实环境
- 验证和迭代会更快

这也是课程后面一直在强调的：  
**MCP 让 AI 看见真实世界。**

## 六、Skill 解决的是“让 AI 像你们团队一样做事”

如果说 MCP 负责现实上下文，那么 `Skill` 负责团队规则上下文。

课程对 Skill 的总结非常清楚：

- 它本质上是一份固定流程模板
- 以 `SKILL.md` 为核心
- 把做某件事的方法、约束和模板封装起来

### 1. Skill 和普通 Prompt 的区别

课程里做了一个很实用的对比：

- 普通 Prompt 需要每次重新描述
- Skill 则更像一套固定 SOP
- 普通 Prompt 更依赖当次质量
- Skill 更强调复用、一致性和全局生效

### 2. Skill 的优势

课程里提到的关键词包括：

- 一致性更强
- 复用性更高
- 上下文成本更低
- 修改一次可以全局复用

换句话说，Skill 是把“团队经验”从口头要求变成可执行资产。

## 七、Skill.md 的结构，本质上是在定义一种自动化任务单元

课程后面把 `SKILL.md` 的结构拆得比较细，这部分非常适合保留为方法论。

### 1. 元数据

通常包括：

- `name`
- `version`
- `author`
- `description`
- `requires`

这部分的作用是描述：

- 这个 Skill 是什么
- 需要哪些依赖
- 适合解决什么问题

### 2. 指令部分

课程用 Markdown 示例说明了：

- 可以按步骤写清执行流程
- 可以包含代码块
- 可以包含多语言片段
- 可以描述输入、输出、依赖和异常

### 3. 执行逻辑

课程把执行过程拆得很清楚：

1. 解析元数据
2. 检查环境依赖
3. 按顺序执行步骤
4. 支持变量传递
5. 允许中断与错误信息反馈
6. 输出结果或日志

### 4. 实践建议

课程里还给了几条很稳的规则：

- 命名清晰、无歧义
- 每一步说明明确
- 先小样本验证再投入生产

这说明 Skill 不是“随手写个说明文档”，而是一个高复用的自动化任务单元。

## 八、为什么 Skill 比“把要求写在 Prompt 里”更适合团队协作

课程里给了一个非常接地气的解释：

- 普通 Prompt 像“你临时交代某人做事”
- Rule 像“公司明文规定”
- MCP / Tools 像“给他一堆软件和 API”
- Skill 像“给他一整套岗位培训大礼包”

这个比喻很适合记忆，也很适合理解它的工程价值：

- Prompt 解决当次任务
- MCP 解决外部能力
- Skill 解决流程模板和团队规范

它们不是竞争关系，而是互补关系。

## 九、VibeCoding 最关键的工程洞察：MCP 和 Skill 分工非常清晰

课程后半段终于把两者放到同一个编码流程里，这部分是整篇最重要的实践结论。

### 1. MCP 负责什么

从表格和流程图里可以概括为：

- 连接数据库
- 获取真实表结构和字段类型
- 查看约束与已有数据
- 在需要时执行 DDL / 查询

### 2. Skill 负责什么

它主要负责：

- 命名与注释规范
- 异常处理模板
- 日志与返回格式
- 团队代码风格

### 3. 二者合起来会发生什么

课程最后用一句话概括得非常准确：

**MCP 让 AI 看见真实世界，Skill 让 AI 遵守团队规范。**

这两层补齐后，AI 生成的代码才更可能既“对世界真实”，又“对项目规范真实”。

## 十、用 VibeCoding 做团队任务管理工具：一句话需求也能跑通完整后端链路

课程最后给出了一个团队任务管理工具的实战案例，技术栈大致是：

- 前端：Vue 3 + Element Plus
- 后端：Spring Boot + MyBatis-Plus
- 数据库：MySQL

功能包括：

- 任务管理
- 成员管理
- 评论与协作
- 看板视图

### 1. 第一步：一句话描述需求

课程演示的关键点不是“把 PRD 写得很细”，而是让 Claude Code 先从一句相对完整的需求开始推进。

### 2. 第二步：Claude Code 借助 MCP 自动创建数据库

借助 MySQL MCP，Claude Code 能做的事情包括：

- 创建数据库
- 建表
- 增加字段
- 查询表结构验证结果

这意味着数据库侧不再完全靠人工来回切换执行。

### 3. 第三步：Claude Code 借助 Skill 自动生成符合规范的代码

课程里给出的约束包括：

- 类名、方法名、注释风格统一
- 异常使用团队规定的 `BusinessException`
- 日志风格统一
- 返回结构统一，例如 `Result<T>`

这样生成出来的 Service / Controller 更接近可直接并入项目的风格。

### 4. 第四步：用 MCP 再做验证和增量迭代

课程后面还演示了：

- 加一个 `tags` 字段
- 新增看板接口
- 批量生成测试数据
- 修改任务状态流转

这说明 VibeCoding 不是“一次性生成完就完了”，而是可以持续做增量迭代。

## 十一、为什么 VibeCoding 的核心不是“快”，而是“快得可控”

课程最后给了一个非常有工程味道的对比：

- 传统开发：手动写 DDL、手动打样板、改一次测一次
- 只用 AI：前后端可能看起来快，但容易脱离真实数据库和团队规范
- MCP + Skill + Claude Code：速度更快，同时上下文和规范更完整

它真正优化的几个点包括：

- 数据库设计：不再全靠猜
- 代码规范：不再全靠事后 Code Review 才发现问题
- 需求迭代：能做小步快跑
- 数据验证：能在真实上下文中快速验证

所以 VibeCoding 的价值，并不只是“帮你省时间”，而是把速度建立在更高的一致性和真实性之上。

## 十二、把这份笔记压缩成一条最适合复习的主线

如果只保留最核心的学习顺序，这篇《VibeCoding与工程化实战》可以压缩成下面这条链：

1. 先安装并跑通 Claude Code CLI
2. 再接受一个现实：只有模型还不够，它看不见真实世界，也不懂团队规范
3. 用 MCP 给 AI 接入数据库、API、文件等真实上下文
4. 用 Skill 把团队 SOP、命名规范、异常模板、日志规范固化下来
5. 理解 `SKILL.md` 是一种可执行的自动化任务单元
6. 把 MCP 和 Skill 同时接入 Claude Code，形成上下文与规则双补全
7. 用一句话需求驱动最小业务闭环，从数据库到后端代码一起生成
8. 在真实上下文中继续增量迭代，而不是一次性生成后全靠人工返工

## 十三、这份课最重要的心法

这份课程真正想说明的不是“Claude Code 很强”，而是：

**AI 编码要想从演示效果走进工程现场，关键不是更花哨的提示词，而是把现实上下文和团队规范都接进来。**

真正可靠的 AI 工程化能力，往往来自三个层面的协同：

- Claude Code：负责生成与执行
- MCP：负责真实世界上下文
- Skill：负责团队规范约束

当这三者配合起来之后，VibeCoding 才不只是“让 AI 帮你写点代码”，而会真正变成一种：

- 能看见现场
- 能遵守规则
- 能持续迭代
- 能进入项目

的工程化开发方式。
