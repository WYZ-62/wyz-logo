# AI Agent开发实战

这份课程笔记不是在抽象讲“什么是 Agent”，而是围绕一个最小可运行案例，把 Agent 从概念拉进了实际搭建过程：先认识平台，再区分 MCP 和 Agent，接着理解 ReAct 与记忆机制，最后通过插件和 Function Calling 做出一个最简版电影查询 Agent。  
如果按学习逻辑重组，它更适合作为一篇“怎么从会用 AI 工具，走到能设计一个 Agent”的实践文章。

## 一、先别急着搭 Agent，先认识它运行的平台和边界

课程一开始先介绍了百宝箱企业版平台，这一步其实很有必要，因为后续 Agent 并不是悬空运行的，而是依托平台能力。

从截图内容可以提炼出两个重点：

- 平台提供了应用创建、插件管理、资源集中和运营能力
- 它更像一个 AI 应用承载环境，而不只是聊天界面

课程里还额外说明了：

- 权限和登录方式要先搞清楚
- 对某些功能的使用边界、Token 限制和账号权限也要提前确认

这提醒我们一个很现实的工程问题：  
很多 Agent 设计问题，表面看是 Prompt 或工具问题，实际上可能先卡在平台权限、运行入口和能力边界上。

## 二、从“工具使用者”到“Agent 设计者”，最大的变化是控制权转移了

课程接着抛出了一个非常关键的问题：

**MCP 和 Agent 到底有什么本质区别？**

### 1. MCP 更像“人来决定调用什么工具”

课程的表格和说明可以概括成：

- 调用什么工具，由人决定
- 场景通常更固定、流程更清晰
- 工具链是辅助人完成任务

### 2. Agent 更像“AI 在目标约束下自己决定怎么推进”

Agent 的特点则是：

- AI 具备一定自主判断能力
- 会根据上下文、目标和反馈动态决策
- 不只是“会调用工具”，还会在调用前后做推理与修正

所以两者最大的区别不是有没有工具，而是：

- MCP 更偏“人主导工具使用”
- Agent 更偏“AI 主导任务推进”

这也是课程标题“从工具使用者到 Agent 设计者”真正想表达的转变。

## 三、Agent 的底层思维方式，不是一次性回答，而是 ReAct 循环

课程后面把 `ReAct` 当成 Agent 的核心机制来讲，这一点非常重要。

### 1. 什么是 ReAct

ReAct 是一种让 AI 在解决问题时不断交替进行：

- `Reasoning` 推理
- `Action` 行动

并把结果再反馈回下一轮推理的交互模式。

课程给出的三字口诀非常适合记忆：

**思 -> 行 -> 反馈 -> 再思**

### 2. ReAct 的基本环节

课程把循环拆成四步：

1. 推理：分析当前问题，形成下一步行动思路
2. 行动：调用工具、查询信息、执行操作
3. 观察：拿到执行结果
4. 重复循环：把观察结果继续喂回推理链

### 3. 为什么 ReAct 更有效

课程里拿它和“直接给答案”的方式做了对比，重点在于：

- 不容易遗漏关键信息
- 可以在中途修正
- 更适合多步任务和复杂问题

这说明 Agent 最关键的进步，不是“能说得更像人”，而是“能在过程中不断调整自己”。

## 四、Agent 不只是会推理，还得会记忆

课程专门讲了智能体里的 `Memory`，也就是跨轮记忆，这部分很适合和 ReAct 放在一起理解。

### 1. 为什么跨轮记忆重要

课程里给了很现实的对比：

- 没有记忆时，用户总要重复说明偏好和上下文
- 有记忆时，系统可以延续之前的交互状态，给出更自然、更个性化的回应

### 2. 记忆通常分成两层

#### 上下文窗口

- 保存最近几轮对话
- 服务当前回合语义理解
- 更偏短期记忆

#### 长期记忆

- 保存用户偏好、历史行为、关键事实
- 更偏持久化信息
- 通常要借助数据库或知识存储

### 3. 工程实现方式

课程里给出三种常见方式：

- 只靠上下文窗口
- 用外部记忆库
- 对记忆做压缩与摘要

这说明 Memory 不是单点功能，而是一套上下文管理机制。

## 五、一个可运行的 Agent，首先要有明确的目标和边界

课程里用“电影查询 Agent”做了最小案例，这个选择很合理，因为它足够简单，又能把 Agent 的关键环节串起来。

这个最简版 Agent 的目标大致是：

- 用户可以自然语言问“今天有什么好看的电影”
- Agent 自动判断是否需要查询电影插件
- 再把结构化结果整理成自然语言回复

这里最关键的不是电影本身，而是通过一个足够小的业务问题，把 Agent 的完整链路跑通。

## 六、System Prompt 决定 Agent 的人格、边界和输出方式

课程里把 `System Prompt` 放在早期配置步骤里，这很合理，因为它实际上是 Agent 的运行规则。

从截图内容可以提炼出，System Prompt 至少要约束：

- 角色设定
- 对话目标
- 回答风格
- 工具调用边界
- 输出格式

课程还明显沿用了前面 Prompt 工程里的思路：  
角色、约束、格式这些内容，不只是提高可读性，而是在给 Agent 设定“工作制度”。

这意味着：

**System Prompt 不是普通提示词，而是 Agent 的操作说明书。**

## 七、插件不是“外挂功能”，而是 Agent 可以动手的手脚

课程接下来进入插件接入，这部分实际上就是让 Agent 拥有外部执行能力。

### 1. 为什么先用 Mock 插件

课程选择先接一个电影查询 Mock 插件，而不是直接接真实服务，这个设计很稳。

因为这样可以先验证：

- Agent 有没有正确决定要不要调用工具
- 参数结构对不对
- 返回结果能不能被正常读取和组织

### 2. 插件描述为什么重要

截图中对插件结构的说明很清楚，通常要定义：

- 插件名称
- 功能描述
- 入参定义
- 返回结果结构

这部分越清楚，模型越容易判断：

- 什么时候该调用
- 该怎么组装参数
- 返回结果该怎么解释

## 八、Function Calling 的本质，是让模型从“会说”变成“会调工具”

课程最后专门讲了 `Function Calling`，这其实是整篇里最关键的底层机制之一。

### 1. Function Calling 是什么

它是 AI Agent 调用外部插件、获取实时数据、执行具体任务的核心机制。

课程里给的标准流程可以压缩为：

1. 识别用户输入
2. 模型推理是否需要外部工具
3. 生成结构化调用参数
4. 平台执行函数或插件
5. 返回结果给模型
6. 模型再把结果组织成自然语言回复

### 2. 模型本身并不执行代码

课程这点讲得很重要：

- LLM 本身只负责决定“要不要调”
- 它不会直接执行外部代码
- 真正执行工具的是平台侧

所以插件的“函数描述”质量非常关键。  
因为模型就是通过这份说明来判断自己能做什么、该怎么做。

### 3. 为什么说插件描述是“艺术”

如果描述不清楚：

- 模型会误判是否调用
- 会错传参数
- 返回结果也更难被用好

这其实和 API 设计很像：  
你定义得越清晰，系统协作越稳定。

## 九、最小可用 Agent 的搭建流程，其实就是一条缩小版工程链

课程里的实操步骤可以整理成这条链：

1. 在平台创建应用
2. 写好 System Prompt
3. 接入最小可用 Mock 插件
4. 配置插件参数与返回结构
5. 绑定插件到 Agent
6. 用测试输入验证 ReAct 流程

这个过程的价值，不在于最后做了一个电影推荐器，而在于你已经能验证：

- Agent 是否理解任务
- 是否会选择工具
- 参数是否组装正确
- 返回结果是否能转成自然语言

换句话说，这是 Agent 设计里的第一条闭环。

## 十、测试 Agent 时，真正要看的不是“答没答出来”，而是“它是怎么答出来的”

课程里专门拿有插件和无插件的版本做了对比，这一步很重要。

### 1. 没有插件时

Agent 更像普通聊天模型：

- 根据已有知识猜答案
- 容易不准
- 缺少实时信息

### 2. 有插件时

Agent 可以：

- 主动调用外部能力
- 获取实时数据
- 按 System Prompt 组织结果

### 3. 真正要关注什么

不是只看“最终答案像不像”，而是要观察：

- 有没有发生工具调用
- 调用参数是否合理
- Observation 是否被正确利用
- 最终回答是否真的基于工具结果

这也是为什么课程会提到检查 Thought / Action / Observation 链路。

## 十一、这个最简版 Agent 做不到什么，同样很重要

课程最后还专门讲了“这个版本做不到什么”，这部分很有价值，因为它提醒我们别把 V1 当成终局。

从截图内容可以总结出，当前简化版 Agent 的局限包括：

- 还不能深度理解复杂偏好
- 还不能进行长期规划
- 还不能真正完成更复杂的跨步骤任务

这说明一个最小可用 Agent 的意义不是“全都做到了”，而是：

- 已经跑通最核心的执行链
- 明确知道下一步还缺什么

## 十二、把这份笔记压缩成一条最适合实战复习的主线

如果只保留最核心的学习顺序，这篇《AI Agent开发实战》可以压缩成下面这条链：

1. 先理解 Agent 依托的平台环境和权限边界
2. 再区分 MCP 和 Agent 的本质差异：谁来决定下一步
3. 理解 ReAct 循环：推理、行动、观察、再推理
4. 补上跨轮记忆：上下文窗口 + 长期记忆
5. 用 System Prompt 给 Agent 设定角色、边界和风格
6. 用插件让 Agent 具备外部执行能力
7. 用 Function Calling 把自然语言任务转成结构化工具调用
8. 通过最小案例验证整条 Agent 闭环
9. 最后明确 V1 做不到什么，再决定下一步演进方向

## 十三、这份课最重要的心法

课程真正想表达的，并不是“Agent 很智能”，而是：

**Agent 的价值，不在于它会说多少，而在于它能否在目标、工具、记忆和反馈之间形成闭环。**

真正决定一个 Agent 是否可用的，通常不是某一句 Prompt，而是这几层能否协同：

- 目标是否清楚
- 规则是否明确
- 工具是否可用
- 记忆是否连续
- 反馈是否能进入下一轮推理

当这些都建立起来之后，Agent 才不只是一个会聊天的模型，而会变成一个能推进任务、能利用工具、能逐步逼近目标的工作系统。
