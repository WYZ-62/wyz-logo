# RAG

这份课程笔记围绕 RAG 展开得很系统：先指出大语言模型本身的知识边界和幻觉问题，再解释为什么要用检索增强，接着进入 RAG 的处理链路和一系列关键优化点，包括分块、Embedding、检索、查询重写、重排序、输入压缩以及答案生成策略。  
如果按学习逻辑重组，它更适合作为一篇“为什么要做 RAG，以及做 RAG 时真正该关注哪些细节”的工程入门与复习文章。

## 一、先承认大模型本身有边界，RAG 才有存在意义

课程一开始先讲了大语言模型的本质与局限，这一步非常关键。

### 1. 大模型本质上在做什么

课程里的表述可以压缩成一句话：

**大语言模型本质上是基于语料统计规律进行模式预测。**

它通过学习海量语料中的语言模式来生成文本，但这并不等于它天然拥有：

- 最新知识
- 权威知识
- 可追溯知识
- 对外部事实永远准确的理解

### 2. 大模型常见的局限

课程里提到几类问题：

- 缺乏真实推理保障
- 知识存在边界
- 训练数据有时效限制
- 答案来源不可追溯

也就是说，大模型“会说”不等于“知道得永远对”。  
而 RAG 正是用来补这层知识边界的。

## 二、RAG 是什么：不改模型参数，把外部知识接进生成链路

课程给出的定义非常清楚：

`RAG`（Retrieval-Augmented Generation）是一种**不修改模型参数**、而是通过检索外部知识并把相关文档注入 Prompt，再让大模型生成答案的技术。

它的关键价值主要体现在三点：

- **知识与能力分离**：知识存储从模型参数中拆出来
- **动态检索增强**：按需从知识库里取最新、最相关的上下文
- **上下文可追溯**：生成依据可以来自明确的检索结果

所以 RAG 不是“让模型变聪明”，而是让模型在回答时拥有更可靠的外部参照。

## 三、RAG 最核心的处理链路，其实只有三步

课程里把 RAG 总结成一个非常清晰的三步流程：

1. 数据处理
2. 检索
3. 生成

### 1. 数据处理

首先要把原始文档准备成可检索的知识库：

- 文本清洗
- 分块
- 向量化
- 存储进向量数据库或知识库

### 2. 检索

根据用户问题在知识库中寻找最相关的片段：

- 计算 query 与文档片段的相似度
- 找到最相关内容
- 作为后续生成的上下文

### 3. 生成

把检索结果和用户问题一起塞进 Prompt：

- 让模型基于上下文回答
- 降低凭空编造的风险

课程里这部分最值得记住的一点是：

**RAG 的本质不是“先搜再答”这么简单，而是把检索能力接进生成链路。**

## 四、Prompt、RAG、微调，解决的不是同一个问题

课程里专门把三种模型优化方法做了定位对比，这部分非常适合做方法选型。

### 1. Prompt Engineering

- 定位：轻量级、低成本优化
- 特点：不微调、无外部知识
- 适用：通用任务、快速迭代

### 2. RAG

- 定位：中等定制化、高外部知识依赖
- 特点：不微调，依赖高质量知识库
- 适用：知识动态更新、强检索型场景

### 3. 微调

- 定位：高度定制化、高资源消耗
- 特点：任务固定、极致性能导向
- 适用：长期稳定任务、追求特定能力

这三者不是替代关系，而更像三种不同的优化层级。  
课程里对 RAG 的定位很准确：

**它是“灵活接入新知识、避免重复训练”的重要选择。**

## 五、RAG 为什么比“直接把知识塞进 Prompt”更实用

课程给了几个很现实的应用场景：

- 单篇文档理解与摘要
- 个人文档助手
- 领域客服系统
- 搜索引擎级应用

这些场景的共同问题是：

- 文档太多
- 知识经常更新
- 单次输入窗口有限

RAG 的价值就在于：

- 先检索，再生成
- 让模型只看和当前问题相关的内容
- 在可用上下文窗口内尽可能提高信息密度

所以它解决的不是“有没有知识”，而是“怎么在有限窗口里把对的知识送进去”。

## 六、知识库分块不是小细节，而是 RAG 质量的起点

课程里对分块策略讲得很实用，而且这确实是很多 RAG 系统最容易踩坑的点。

### 1. 为什么一定要分块

因为原始文档通常太长，不能直接整体参与检索和输入。  
知识库必须切成更小的文本块 `chunk`。

### 2. 分块太大有什么问题

- 容易引入噪音
- 超出大模型上下文窗口

### 3. 分块太小有什么问题

- 容易丢失语义
- 上下文连续性变差

### 4. 常见分块方式

课程里列出三种典型方式：

- 固定大小分块：按 token 或字符数均匀切分
- 基于标题结构的规则分块：按标题、段落等边界切
- 内容感知型分块：依据语义单元进行切分

这部分的本质不是“选一个花哨算法”，而是：

**在召回粒度和语义完整性之间找到平衡。**

## 七、Embedding 决定了“相似”在检索系统里是怎么被表示的

课程里把文本向量化和 Embedding 模型选择单独讲了一节，这一步对 RAG 非常关键。

### 1. 什么是文本向量化

文本向量化就是把文本变成高维向量，让语义相近的文本在向量空间中更接近。

### 2. 短文本与长文本的区别

课程里提到：

- 短文本向量化聚焦局部语义
- 长文本向量化更关注整体主题

这意味着：

- 文本长度和分块方式
- Embedding 模型的选择

其实是耦合在一起的。

### 3. 模型选择不是越专越好

课程里给出的建议很务实：

- 多数场景直接用通用 Embedding 模型
- 只有在医学、法律等强专业领域，才更值得考虑专门微调

所以 RAG 的第一原则往往不是“先定制模型”，而是先把知识组织和检索链打磨顺。

## 八、向量数据库的意义，不是“存向量”，而是“更快地找相关内容”

课程里把向量数据库的目标描述得很明确：

- 提高相似性检索效率
- 确保高召回且与精度匹配

### 1. 最朴素的方法：暴力比对

适合小规模数据，但随着数据量增长会明显变慢。

### 2. 更高级的索引结构

课程里提到了几类思路：

- 链式结构
- 树状结构
- 图结构

这些索引结构的共同目标只有一个：

**提升召回量与检索速度。**

### 3. 检索质量依赖什么

课程里点出两个关键因素：

- 分块质量
- 向量化质量

也就是说，向量数据库本身不是万能药，上游数据组织同样决定最终效果。

## 九、用户的原始问题，往往不是最适合检索的问题

这也是课程里专门讲“查询重写”的原因。

### 1. 为什么要做查询重写

用户提问常见问题包括：

- 表达不清
- 太口语化
- 信息缺失
- 一个问题里混了多个子问题

### 2. 查询重写要做什么

课程里提到：

- 对原问题改写同义词表达
- 生成多个语义接近的查询变体
- 多路检索后合并结果

它的目标是：

- 提升召回覆盖率
- 降低因为措辞差异造成的漏检

### 3. 单步与多步查询分解

课程还提到了：

- 单步拆分：把复杂问题拆成多个并行小问题
- 多步拆分：前一步结果影响后一步查询

这说明复杂检索不一定是一发入魂，而可以被拆成更可控的推理式流程。

## 十、HIDE 的思路很巧：先假设答案，再拿假设去搜

课程里提到 `HIDE`（Hypothetical Document Embeddings），这是一个很有代表性的检索优化思路。

它的核心思想是：

- 先让模型生成一个“假设答案”
- 再用这个假设答案去做向量检索

这样做的好处在于：

- 真正问题和答案在语义空间里往往更接近
- 可以弥补“问题太短、检索方向不清”的问题
- 在高精度检索场景里尤其有效

这类方法很能体现 RAG 的一个特点：  
并不是只有知识库重要，查询组织方式同样会显著影响结果。

## 十一、召回之后还不够，重排序才决定谁进最终 Prompt

课程里对“重排序”的定位很准确：

重排序是在检索之后，按相关性、时效性、业务规则等再筛一遍，确保最关键的信息排到前面。

### 1. 为什么需要重排序

因为召回结果里常常会出现：

- 表面相似但不够关键的内容
- 太旧的内容
- 语义相关但业务价值不高的内容

### 2. 常见重排序维度

课程里提到：

- 基于 TF-IDF / PageRank 的重要性排序
- 基于时效性的时间排序
- 结合业务偏好的个性化排序

### 3. 工程价值

课程给出的结论非常实用：

- 重排序能减少 token 限制带来的关键信息丢失
- 它是连接检索与生成的核心环节
- 会直接影响最终回答质量

所以 RAG 的关键不只是“召回多少”，还包括“最终送进去的是哪几段”。

## 十二、输入压缩与过滤，是把高召回结果变成高质量上下文的关键一步

课程后面专门讲了 RAG 输入前的知识压缩与过滤，这一步很容易被低估。

### 1. 信息压缩

目标是：

- 提炼长文本的核心内容
- 避免无效信息挤占 token 窗口

### 2. 噪声过滤

目标是：

- 删除不相关条目
- 减少无关干扰

### 3. 为什么这一步重要

课程里点出三点价值：

- 提升信息密度
- 降低注意力偏移风险
- 为高质量输入打基础

换句话说，召回不是终点，把召回结果“整理干净”同样重要。

## 十三、RAG 的答案生成方式，也可以按成本和稳定性分层

课程最后把答案生成大致分成三类：

### 1. 单次回答

- 一次性整合问题与检索知识
- 直接生成答案

优点是简单，缺点是容易受单次生成波动影响。

### 2. 修正式回答

- 通过迭代引入新知识
- 逐步修正答案

更适合需要多轮补充和校正的场景。

### 3. 紧凑式回答

- 每次调用尽量控制 token 量
- 追求更低成本与更稳定的资源占用

这也说明，RAG 的生成层不只是“把材料塞进去让模型回答”，而是可以继续做成本与效果的工程化平衡。

## 十四、把这份笔记压缩成一条最适合复习的主线

如果只保留最核心的学习顺序，这篇 RAG 笔记可以压缩成下面这条链：

1. 先承认大模型本身存在知识边界和幻觉问题
2. 再理解 RAG 是“不改参数、引入外部知识”的增强方案
3. 理清数据处理、检索、生成三步主流程
4. 学会区分 Prompt、RAG、微调各自解决的问题
5. 把分块、Embedding、向量索引当作知识检索的基础设施
6. 通过查询重写、单步/多步拆分、HIDE 提高召回
7. 用重排序、压缩和过滤提高上下文质量
8. 最后根据成本和稳定性设计答案生成策略

## 十五、这份课最重要的心法

课程真正想说明的，不是“RAG 很火”，而是：

**RAG 的本质，是把知识组织能力、检索能力和生成能力接成一条可控链路。**

真正决定效果的，并不只有模型本身，还包括：

- 你怎么切知识
- 你怎么表示知识
- 你怎么搜知识
- 你怎么筛知识
- 你怎么把知识喂给模型

当这些环节都被认真设计以后，RAG 才不是“外挂知识库”，而会真正变成一个可靠、可追溯、可持续迭代的 AI 应用基础设施。
