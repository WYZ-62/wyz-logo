# Java后端基础习题（五）

这组题对应 6 月 14 日的练习，重点放在 Spring Boot 测试、微服务架构、Saga、GitFlow、RAG 与分布式一致性方案选择。

## 单选题

### 1. 为了在 Spring Boot 应用中自动配置测试环境，应当使用哪个注解？

- A. `@Autowired`
- B. `@SpringBootTest`
- C. `@Configuration`
- D. `@ComponentScan`

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>B</p>
<p><strong>知识点：</strong>Spring Boot 测试启动方式，以及测试上下文加载的核心注解。</p>
<p><strong>解题思路：</strong><code>@SpringBootTest</code> 用于启动完整或接近完整的 Spring Boot 应用上下文，是最常见的集成测试入口注解。它会帮助测试类加载 Spring 容器、自动配置环境，因此答案选 B。</p>
<p><strong>易错点：</strong><code>@Autowired</code> 只是依赖注入；<code>@Configuration</code> 用于声明配置类；<code>@ComponentScan</code> 用于组件扫描。它们都不是专门用来“启动测试环境”的注解。</p>
</details>

### 2. 在微服务架构中，需要使用真实的数据库或消息队列（而非 Mock）来验证服务与这些外部依赖之间的交互是否正确（如 SQL 查询、消息序列化）。以下哪种测试类型最符合这一目标？

- A. 单元测试——通常 Mock 掉外部依赖，只验证内部逻辑
- B. 组件测试——将单个服务作为整体进行黑盒验证，外部依赖可 Mock 也可真实
- C. 集成测试——专门验证服务与真实外部依赖之间的交互边界
- D. 端到端测试——验证跨多个服务的完整业务流程

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>C</p>
<p><strong>知识点：</strong>单元测试、组件测试、集成测试、端到端测试的目标边界区别。</p>
<p><strong>解题思路：</strong>题目强调的是“使用真实数据库或消息队列，验证服务和外部依赖之间的交互是否正确”。这正是集成测试的典型目标：验证服务和真实依赖之间的接口边界、数据格式、序列化和查询行为。因此 C 最符合题意。</p>
<p><strong>易错点：</strong>B 容易被选中，因为组件测试确实会把单个服务作为整体来测。但题目点得非常明确：需要验证和真实外部依赖的交互，这正是集成测试的核心定义。D 则范围更大，通常关心跨服务完整流程，不是题目最聚焦的测试层次。</p>
</details>

### 3. 分布式事务 Saga 模式的特点是什么？

- A. 依赖两阶段提交协议。
- B. 依赖长事务的一系列本地事务步骤。
- C. 所有步骤都必须在一个数据库事务中完成。
- D. 一次只能有一个本地事务步骤运行。

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>B</p>
<p><strong>知识点：</strong>Saga 模式的基本思想：把长事务拆成多个本地事务，并通过补偿实现最终一致性。</p>
<p><strong>解题思路：</strong>Saga 的核心不是 2PC，也不是单一数据库事务，而是把一个大事务拆成多个本地事务步骤，每个步骤成功后继续推进，失败时通过补偿动作回滚之前的影响。因此 B 描述最准确。</p>
<p><strong>易错点：</strong>A 是把 Saga 和 2PC 混淆了；C 则违背了分布式事务拆分的本意；D 说法过于绝对，Saga 的关键不是“一次只能一个步骤”，而是“多个本地事务按业务编排形成长事务”。</p>
</details>

### 4. 某团队采用 GitFlow 工作流进行管理，`feature/payment` 分支完成开发后合并至 `develop` 分支。合并后发现 `develop` 分支的 `application.yml` 配置文件中的数据库连接池配置被覆盖为旧版本的默认值。开发团队确认在本地从未执行过 `git reset` 或文件回滚操作。问题：导致该配置文件被覆盖的最可能原因是什么？

- A. 使用了 `rebase` 操作导致提交历史线性化，覆盖了 `develop` 分支的原始 `HEAD`
- B. 采用普通 `merge` 操作且 `develop` 分支未定期同步 `master` 分支的最新配置
- C. 合并冲突解决时误选了 `feature` 分支中的旧版本配置文件并提交
- D. Git LFS 未正确跟踪大文件，导致元数据同步时覆盖了配置文件

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>C</p>
<p><strong>知识点：</strong>Git 分支合并中的冲突解决机制，以及“文件内容被旧版本覆盖”最常见的人为原因。</p>
<p><strong>解题思路：</strong>题目已经说明没有执行 <code>reset</code> 或回滚操作，因此更可能是在 merge 冲突处理中选错了版本。配置文件这类高频改动文件，一旦 feature 和 develop 都改过，就很容易发生冲突；如果在解决冲突时误保留了 feature 分支里的旧配置并提交，就会出现“合并后被旧值覆盖”的结果，因此 C 最合理。</p>
<p><strong>易错点：</strong>A 容易被误选，因为很多人对 rebase 有“会覆盖别人内容”的心理印象，但 rebase 本身不会凭空把特定配置改回旧值。B 只是同步策略问题，不足以直接解释“为什么恰好回到旧默认值”。D 与普通文本配置文件几乎无关。</p>
</details>

### 5. 某大语言模型的上下文窗口标称容量为 8k Tokens。一位用户提交了一篇约 9000 字的中文技术文档进行摘要，系统成功处理且未触发长度限制警告。以下哪项解释最符合 Token 计算的实际原理？

- A. 模型在预处理阶段自动过滤了文档中的数字和标点符号，降低了总 Token 数
- B. 中文编码器采用字级别切分，单个汉字独立计为 1 个 Token
- C. 一个 Token 可对应一个完整汉字或多个汉字组成的词组，实际 Token 数通常少于字符数
- D. 系统检测到文档接近上限时，自动启用了语义压缩算法合并相邻句子

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>C</p>
<p><strong>知识点：</strong>Token 与字符数的关系，以及中文文本在分词编码中的实际情况。</p>
<p><strong>解题思路：</strong>字符数和 Token 数不是一一对应关系。一个 Token 可能对应一个汉字，也可能对应多个字组成的片段、词组或子词单位，因此 9000 字的中文文本并不必然等于 9000 Tokens，实际 Token 数可能低于字符数，所以系统仍有可能在 8k 上下文窗口内成功处理。</p>
<p><strong>易错点：</strong>B 听起来很合理，因为很多人会把“中文一个字”直接等同于“一个 Token”，但实际分词器并不是这么机械。A 和 D 则属于题干没有给出的额外机制，不能凭空假设系统做了这些特殊处理。</p>
</details>

## 多选题

### 6. 以下哪些技术可以提高 RAG 的效果？

- A. 文档分块策略优化
- B. Embedding 模型选择
- C. 重排序（Rerank）
- D. 查询改写（Query Rewrite）

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>A、B、C、D</p>
<p><strong>知识点：</strong>RAG 提效的常见优化点，包括切分、向量表示、检索后重排和查询增强。</p>
<p><strong>解题思路：</strong>文档分块会影响检索粒度和语义完整性；Embedding 模型决定召回质量；Rerank 可以在召回后提升排序准确性；Query Rewrite 能把用户问题改写得更适合检索。这四项都直接作用于 RAG 链路质量，因此全部正确。</p>
<p><strong>易错点：</strong>容易只关注 Embedding，而忽视“切分”和“重排”的重要性。很多 RAG 效果差，并不是模型太弱，而是 chunk 不合理、检索没召全、排序没排准。</p>
</details>

### 7. 分库分表之后会引入哪些新挑战或问题？

- A. 跨分片 JOIN 查询性能下降
- B. 分布式事务的 ACID 保证变复杂
- C. 全局唯一 ID 的生成需求出现
- D. 数据库连接数反而比单库模式下减少

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>A、B、C</p>
<p><strong>知识点：</strong>分库分表带来的典型工程复杂度，包括查询、事务和主键生成问题。</p>
<p><strong>解题思路：</strong>一旦数据分散到多个分片，跨分片 JOIN 往往变难且性能下降，所以 A 正确；事务跨分片后，不再是单库本地事务，ACID 保证复杂度显著提升，因此 B 正确；多个分片同时写入时，也通常需要引入雪花算法、号段模式等全局唯一 ID 方案，所以 C 正确。D 不成立，因为分库分表后系统通常会连接更多实例，连接管理反而更复杂，不会天然减少连接数。</p>
<p><strong>易错点：</strong>很多人只记得“分库分表能扩容”，却忽略了它本质上是“用复杂度换容量”。一旦拆分，查询、事务、主键、运维和路由都会变得更麻烦。</p>
</details>

### 8. RAG 链路中可能出现的“丢上下文”问题，以下哪些是常见原因？

- A. Chunk 切分过小，丢失段落间的语义关联
- B. 检索 Top-K 设置过低，遗漏关键文档
- C. Embedding 模型与生成模型来自不同厂商
- D. 上下文窗口限制导致检索内容被截断

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>A、B、D</p>
<p><strong>知识点：</strong>RAG 中上下文丢失的常见来源：切分问题、召回不足和窗口截断。</p>
<p><strong>解题思路：</strong>Chunk 太小会把原本连续的语义切碎，A 正确；Top-K 太低可能导致关键文档没有被召回，B 正确；即便召回到了，如果总上下文超出窗口限制，后面的内容仍可能被截断，所以 D 也正确。C 不是“丢上下文”的直接常见原因，不同厂商模型可能带来效果差异，但不等同于上下文必然丢失。</p>
<p><strong>易错点：</strong>很多人会把“检索效果不好”和“上下文丢失”完全混为一谈。真正的丢上下文通常有比较明确的链路原因：切碎了、没召回、塞不进去，而不是单纯因为模型厂商不同。</p>
</details>

### 9. 设计 Multi-Agent 系统时，以下哪些组件是必要的？

- A. Agent 定义（角色、能力、目标）
- B. 通信机制（Agent 间消息传递）
- C. 协调机制（任务分配、冲突解决）
- D. 监控和日志

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>A、B、C、D</p>
<p><strong>知识点：</strong>Multi-Agent 系统的基本组成，包括角色建模、通信、协调和可观测性。</p>
<p><strong>解题思路：</strong>没有 Agent 定义，就无法知道每个 Agent 做什么；没有通信机制，Agent 之间无法协作；没有协调机制，任务分配与冲突处理会混乱；没有监控和日志，系统出了问题几乎无法排查。因此四项都属于实际可运行 Multi-Agent 系统的必要组成部分。</p>
<p><strong>易错点：</strong>很多人会把监控和日志视为“上线以后再补”，但对 Multi-Agent 这类多角色协同系统来说，可观测性不是锦上添花，而是最基本的运维与调试前提。</p>
</details>

## 问答题

### 10. 在微服务架构中，服务 A 调用服务 B。为了保证数据一致性，你会在以下两种方案中选择哪一种？

- 方案一：使用分布式事务（如 Seata AT 模式）
- 方案二：使用本地事务 + 异步消息（如 RocketMQ 事务消息）

请给出你的选择，并说明一条你认为最关键的理由。

<details>
<summary>查看参考答案与解析</summary>
<p><strong>答案：</strong>我通常优先选方案二：本地事务 + 异步消息。最关键的理由是它避免了长事务锁资源，更适合微服务高并发场景，在性能、可用性和扩展性上通常更稳。</p>
<p><strong>知识点：</strong>强一致性方案与最终一致性方案在微服务架构中的取舍逻辑。</p>
<p><strong>解题思路：</strong>这类问答题没有绝对唯一答案，关键在于是否能说清“为什么这样选”。如果场景是高并发互联网业务，通常更倾向本地事务 + 事务消息，因为它能显著降低分布式锁和长事务带来的系统压力，同时通过消息机制实现最终一致性。只有在极端强调强一致、且业务可接受性能损耗时，才更可能优先选 Seata AT 这类分布式事务方案。</p>
<p><strong>易错点：</strong>容易把答案写成“分布式事务更强，所以一定选方案一”。真实工程里不是一致性越强越好，而是要在一致性、性能、可用性和复杂度之间做平衡。只给结论、不讲取舍依据，通常拿不到高分。</p>
</details>
