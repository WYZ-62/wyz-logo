# Java后端基础习题（二）

这组题对应 6 月 12 日的练习，重点覆盖 RocketMQ、缓存一致性、分布式事务、微服务容错，以及 AI 编码助手在高 Token 水位下的上下文问题。

## 单选题

### 1. 在智能编码助手的调试会话中，系统连续处理了 15 次代码重构请求，第 16 次请求涉及跨模块的接口重命名。监控面板显示 Token 水位：96.7%，随后 AI 输出的重构方案中，`api_gateway.py` 文件缺少了必要的 `@route` 装饰器。会话参数配置为：`output_limit=3072`，`context_buffer=6144`。

当前配置：

- `context_compression: adaptive`
- `split_mode: function_boundary`
- `summary_fallback: enabled`

问题：造成装饰器遗漏的最主要原因是什么？

- A. `output_limit` 设置偏小导致响应在生成过程中被提前截断
- B. `function_boundary` 切分模式使装饰器与函数定义被分隔在不同片段
- C. `summary_fallback` 启用后摘要模式丢失了装饰器元数据
- D. 未配置 `cross_file_tracking` 导致跨文件引用脱节

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>B</p>
<p><strong>知识点：</strong>高 Token 水位下的上下文压缩机制，以及摘要回退对代码结构元数据的影响。</p>
<p><strong>解题思路：</strong>这道题真正的问题点在于 <code>split_mode: function_boundary</code>。当系统按函数边界切分时，装饰器这类依附于函数定义前后的结构信息更容易被拆散，尤其在后续重构生成时出现遗漏。题干里的高 Token 水位和摘要回退会加剧问题，但最主要的触发点还是切分方式本身，因此选 B。</p>
<p><strong>易错点：</strong>C 看起来也像原因，但它更偏向“摘要压缩后信息丢失”的泛化解释；题目要考的是具体哪种配置最容易导致装饰器和函数定义分离，所以应优先选 B。</p>
</details>

### 2. 某电商平台在“双 11”大促期间需要支撑峰值每秒 8 万单的订单处理能力，核心链路包括库存扣减、订单创建和支付回调。以下哪种架构方案最能满足高并发与数据一致性要求？

- A. 单台 PostgreSQL 数据库 + 单体应用部署
- B. MySQL 主从复制 + 应用服务器集群 + Memcached 缓存层
- C. 分布式数据库分片 + 微服务集群 + 多级缓存（本地 + 分布式）+ 异步消息队列削峰
- D. MongoDB 分片集群 + 无状态容器化应用

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>C</p>
<p><strong>知识点：</strong>高并发电商架构设计中的扩展性、削峰能力、缓存体系与一致性治理。</p>
<p><strong>解题思路：</strong>题目要求同时满足“8 万单/秒的高并发能力”和“核心链路的一致性要求”。这类场景下，单机数据库和单体部署显然扛不住；只有主从复制加缓存，也很难真正解决写入热点和峰值洪峰问题。最合理的方案通常是分库分片承接写压力，微服务集群承接横向扩展，多级缓存承担高频读流量，再用消息队列做削峰填谷和异步解耦，因此 C 最符合大型促销场景的工程实践。</p>
<p><strong>易错点：</strong>B 看起来像经典互联网架构，但它主要解决的是“读扩展”和“部分服务扩容”，对极端写峰值、库存热点、异步回调解耦等问题支持不够。D 的分片和无状态容器能解决部分扩展性问题，但题目强调的是订单、库存、支付这种强业务链路，单靠 MongoDB 分片并不能自然满足一致性要求。</p>
</details>

### 3. 下列关于 Spring Cloud Sleuth 不正确的是（）

- A. Spring Cloud Sleuth 是一个在应用中实现日志跟踪的强有力的工具
- B. 使用 Sleuth 库可以应用于计划任务、多线程服务或复杂的 Web 请求，尤其是在一个由多个服务组成的系统中
- C. Sleuth 可以与日志框架 Logback、SLF4J 轻松地集成，通过添加独特的标识符来使用日志跟踪和诊断问题
- D. 在 Spring Boot Web 应用中增加 Sleuth 非常复杂

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>D</p>
<p><strong>知识点：</strong>Spring Cloud Sleuth 的作用与基本接入成本。</p>
<p><strong>解题思路：</strong>Sleuth 的核心能力是为分布式调用链打上 TraceId、SpanId，方便日志追踪和问题诊断。它能用于 Web 请求、异步任务、多线程和计划任务场景，也能较方便地和常见日志框架配合使用，因此 A、B、C 都是正确描述。反过来看，D 说“增加 Sleuth 非常复杂”明显不符合实际，所以它才是不正确项。</p>
<p><strong>易错点：</strong>这题考的是“不正确的是哪项”，很容易顺手去找正确项。做这类题时一定要先审题。另外，“功能强”不代表“接入复杂”，Sleuth 之所以常被使用，正是因为它接入门槛相对不高。</p>
</details>

### 4. 在消息中间件系统设计中，为何选择队列而非栈来保证消息顺序？

- A. 队列支持随机访问消息内容
- B. 队列天然满足生产者-消费者场景的时序一致性要求
- C. 队列操作的时间复杂度均为 O(1)
- D. 队列能自动过滤重复消息

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>B</p>
<p><strong>知识点：</strong>队列（FIFO）与栈（LIFO）的数据结构差异，以及消息系统为什么更适合 FIFO 语义。</p>
<p><strong>解题思路：</strong>消息中间件最常见的诉求是“先来的消息先处理”，也就是生产顺序和消费顺序尽量一致。队列的先进先出（FIFO）特性天然符合生产者-消费者模型中的时序一致性要求，因此 B 正确。栈是后进先出，显然不适合大多数消息处理场景。</p>
<p><strong>易错点：</strong>C 虽然很多实现里队列操作也可以做到接近 O(1)，但这不是本题选择队列而非栈的核心原因。消息系统本质上要解决的是处理顺序问题，而不是只看操作复杂度。</p>
</details>

### 5. 在设计消息中间件时，使用队列结构最适合处理以下哪种场景？

- A. 高优先级消息立即抢占处理
- B. 保证消息处理的严格时间顺序
- C. 根据消息内容动态跳转处理流程
- D. 消息处理状态的随机回溯

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>B</p>
<p><strong>知识点：</strong>队列结构在消息系统中的适配场景，特别是 FIFO 对顺序消费的支持。</p>
<p><strong>解题思路：</strong>队列最适合的就是“谁先进入，谁先处理”的场景。因此当系统需要保证消息按时间顺序依次消费时，队列是最自然的数据结构选择，所以答案是 B。A 更像优先级队列或调度系统的诉求，C 和 D 则不是普通 FIFO 队列的核心设计目标。</p>
<p><strong>易错点：</strong>很多人看到“消息中间件”会联想到各种高级能力，比如优先级、路由、回溯，但本题问的是“使用队列结构最适合哪种场景”。要先回到队列本身最本质的特征：先进先出。</p>
</details>

## 多选题

### 6. 在微服务架构中，以下哪些是实现服务间通信时需要考虑的容错策略？

- A. 超时控制（Timeout）—— 为远程调用设置合理的超时时间
- B. 重试（Retry）—— 对幂等操作进行有限次重试
- C. 熔断（Circuit Breaker）—— 在错误率超过阈值时快速失败
- D. 舱壁隔离（Bulkhead）—— 限制并发调用数，防止单个服务故障拖垮整个系统

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>A、B、C、D</p>
<p><strong>知识点：</strong>微服务通信中的常见容错模式，包括超时、重试、熔断和隔离。</p>
<p><strong>解题思路：</strong>服务间调用一旦失败，最怕的是故障扩散和资源被拖死。超时可以避免请求无限等待；重试适合幂等操作的瞬时故障恢复；熔断能在连续失败时快速失败，避免雪崩；舱壁隔离则通过线程池、连接池或并发数隔离，防止一个下游故障拖垮整个调用链。因此四项都属于标准容错策略。</p>
<p><strong>易错点：</strong>有些人会把这些策略看成“可选优化”，但在微服务系统里，它们本质上属于稳定性设计的基础设施。尤其是重试一定要和“幂等性”绑定，否则容易把故障放大成重复写入问题。</p>
</details>

### 7. 关于 Java 集合的遍历，以下哪些方式在遍历过程中可以安全地删除元素？（多选）

- A. 使用普通 for 循环（索引遍历）并调用 `list.remove(i)`
- B. 使用 `Iterator` 遍历并调用 `iterator.remove()`
- C. 使用增强 for 循环（for-each）并调用 `list.remove()`
- D. 使用 Java 8 的 `removeIf()` 方法

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>B、D</p>
<p><strong>知识点：</strong>Java 集合遍历时的安全删除方式，以及 <code>ConcurrentModificationException</code> 的常见触发场景。</p>
<p><strong>解题思路：</strong><code>Iterator.remove()</code> 是迭代器语义下官方推荐的安全删除方式，因此 B 正确。Java 8 的 <code>removeIf()</code> 由集合自身控制遍历与删除流程，也属于安全做法，所以 D 正确。增强 for 本质上也是基于迭代器，遍历过程中直接调用 <code>list.remove()</code> 容易触发并发修改异常，所以 C 错误。A 虽然在某些场景下通过手动控制索引可以工作，但题目表述并未说明索引回退或倒序遍历，因此不作为标准安全答案。</p>
<p><strong>易错点：</strong>很多人会把“能删”与“安全地删”混在一起。索引循环确实有时可以删除成功，但如果不处理索引偏移，容易漏删或跳删元素；而增强 for 中直接删集合是最典型的面试陷阱。</p>
</details>

### 8. 在分布式事务解决方案中，以下关于 TCC（Try-Confirm-Cancel）模式的描述，正确的有哪些项？

- A. TCC 是一种柔性事务方案，适用于对一致性要求高但允许短暂不一致的场景
- B. Try 阶段负责业务资源预留，Confirm 阶段执行实际提交，Cancel 阶段回滚预留资源
- C. TCC 方案需要业务代码进行侵入式改造，实现 Try、Confirm、Cancel 三个接口
- D. TCC 天然支持自动处理悬挂事务和空回滚问题，无需额外设计

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>A、B、C</p>
<p><strong>知识点：</strong>TCC 的三阶段语义、适用场景，以及对业务代码的侵入性要求。</p>
<p><strong>解题思路：</strong>TCC 的核心思想就是把一次业务操作拆成 Try、Confirm、Cancel 三步。Try 负责预留资源，Confirm 负责正式提交，Cancel 负责释放或回滚预留资源，因此 B 正确。由于这三个阶段都需要业务自己实现对应逻辑，所以 TCC 明显具有业务侵入性，C 正确。A 也成立，因为 TCC 常用于一致性要求较高、但允许在阶段执行中短暂不一致的场景。D 则错误，悬挂事务、空回滚、幂等问题都需要额外设计，TCC 不会自动替你解决。</p>
<p><strong>易错点：</strong>最容易错的是 D。很多人会以为只要用了 TCC，中间态、重试、空回滚这些问题就都被框架自动兜住了。实际上，TCC 真正的难点恰恰在业务侧补齐这些边界治理。</p>
</details>

### 9. 以下关于分布式系统高可用设计的描述，哪些是正确的？

- A. 冗余部署（多副本）是提高系统可用性的基础手段，通过负载均衡实现流量分发
- B. 故障转移（Failover）机制应配合健康检查，自动将流量切换到健康节点
- C. 异地多活架构可以将流量分散到不同地域的数据中心，实现地域级容灾
- D. 可用性达到 99.99%（四个 9）的系统允许每年宕机时间不超过约 52 分钟

<details>
<summary>查看答案与解析</summary>
<p><strong>答案：</strong>A、B、C、D</p>
<p><strong>知识点：</strong>高可用设计中的冗余、故障转移、异地多活，以及可用性指标换算。</p>
<p><strong>解题思路：</strong>A、B、C 都是高可用设计中的经典做法：多副本提升冗余度，健康检查配合故障转移实现自动切换，异地多活提供地域级容灾能力。D 也正确，因为四个 9 的年可用性意味着全年可接受的不可用时间大约为 52 分钟左右，这是常见的可用性换算结论。</p>
<p><strong>易错点：</strong>很多人知道“三个 9”“四个 9”这些术语，但不知道对应的宕机时间级别。做题时如果对换算不熟，可以记一个常见结论：四个 9 大约是每年 52 分钟，五个 9 大约是每年 5 分钟级别。</p>
</details>

### 10. 请列举几个你用过的联调测试工具，结合实际说说联调中遇到过哪些坑？（100 字内）

<details>
<summary>查看参考答案与解析</summary>
<p><strong>答案：</strong>我常用 Postman、Apifox、Swagger、JMeter。联调常见坑有环境变量不一致、时区格式错误、幂等没处理、回调签名和字段约定不统一。</p>
<p><strong>知识点：</strong>联调测试工具的常见选型，以及接口联调中高频出现的问题类型。</p>
<p><strong>解题思路：</strong>这类问答题重点不是列工具越多越好，而是要体现“工具 + 实际踩坑经验”。常见工具可以列接口调试类（Postman、Apifox、Swagger）和压测类（JMeter），再点出联调时最常见的实际问题，如环境配置不一致、字段含义不统一、签名验证失败、时区和时间格式错误等，这样答案更像真实项目经验。</p>
<p><strong>易错点：</strong>容易把答案写成纯工具清单，缺少实际问题；或者只说“接口不通”“参数错了”这类过于泛化的话。问答题更看重你是否能说出真实项目里经常踩到的具体坑。</p>
</details>
