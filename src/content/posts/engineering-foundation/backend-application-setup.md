# 后端应用搭建

这份课程笔记主线其实很清晰：先理解 Java Web 技术栈和分层思想，再完成 Spring Boot 项目初始化，最后落到接口开发、配置排查和开发效率工具上。  
如果按学习逻辑重组，它更适合作为一篇“后端应用从 0 到能跑起来”的入门与复习文章。

## 一、先理解技术栈为什么会演进

后端应用搭建不能只停留在“把项目跑起来”，还要知道为什么今天大多数 Java Web 项目会采用 Spring Boot、MVC 和分层架构。

### 1. Java Web 技术栈的演进

早期 Java Web 常见做法是：

- `JSP + JavaBean`
- 页面展示和后端逻辑耦合较重
- 前后端逻辑混在一起，维护成本高

后续引入 Servlet 后，技术栈开始往更清晰的职责划分发展：

- 请求处理和页面展示逐步分离
- 代码组织性提升
- 控制层与表现层边界更清楚

这背后的本质，不是技术名词变多了，而是系统复杂度提高以后，必须通过分层来降低维护成本。

### 2. MVC 的核心思想

MVC 的核心是 **关注点分离（SoC）**：

- `Model`：负责数据和业务逻辑
- `View`：负责页面展示
- `Controller`：负责请求分发与流程控制

它解决的是“职责边界不清”的问题。  
如果没有这层抽象，项目很容易出现：

- 页面和业务强耦合
- 功能变更牵一发动全身
- 逻辑散落在多个位置，难以追踪

### 3. 传统 MVC 的局限

随着前后端分离成为主流，传统 MVC 也暴露出明显问题：

- 后端直接渲染 HTML，性能和协作效率受限
- 前后端职责仍容易混杂
- 复杂业务增长后，领域逻辑分散、维护困难

因此后端应用的主流方向逐步变成：

- 通过 API 接口传输数据
- 后端专注数据与业务逻辑
- 前端专注展示和交互

这也是现代后端应用搭建时，默认会采用 REST 风格接口和分层架构的原因。

## 二、理解 SSM 与 Spring Boot 在项目中的角色

### 1. SSM 的组成与分工

课程里对 SSM 的总结非常值得保留：

- `Spring`：IoC 容器，负责对象管理与依赖注入
- `Spring MVC`：处理 HTTP 请求分发和控制器调度
- `MyBatis`：负责数据访问、SQL 映射和结果封装

可以把它理解成一个很稳定的职责链：

1. 浏览器发起 HTTP 请求
2. `Controller` 接收并分发请求
3. `Service` 承担业务逻辑
4. `Mapper / DAO` 访问数据库
5. 数据库返回结果，再逐层返回给调用方

这也是后端应用最基础的调用链路。

### 2. Spring Boot 与 Spring 的关系

Spring Boot 不是替代 Spring，而是对 Spring 的封装与增强。

可以直接记住这几个结论：

- Spring Boot 是基于 Spring 的快速开发框架
- 它的目标是简化配置、加快开发、方便独立部署
- 底层依然依赖 Spring 的 IoC、AOP 等核心机制

它的主要优势包括：

- 自动装配，减少显式 XML 配置
- 约定优于配置，提高上手速度
- `Starter` 机制把常用技术栈打包组合好
- 内嵌服务器，方便直接启动和部署

所以理解 Spring Boot 的关键不是“会不会用”，而是知道：

- 它帮你省掉了哪些样板配置
- 它仍然建立在 Spring 原理之上
- 当自动装配失效或配置冲突时，你要能往底层回溯

## 三、项目初始化是后端应用搭建的第一道门槛

### 1. 创建 Spring Boot 项目时要先配对基础坐标

在 IntelliJ IDEA 中通过向导创建 Spring Boot 项目时，首先要确认：

- 项目名称与存储路径
- 语言选择为 `Java`
- 构建工具选择 `Maven`
- JDK 版本满足要求

其中最容易被忽略，但最重要的是两个 Maven 坐标：

- `groupId`
- `artifactId`

它们共同构成项目的 Maven 依赖坐标，用于：

- 依赖管理
- 构件标识
- 项目命名和后续打包发布

### 2. JDK 版本要和 Spring Boot 版本匹配

课程截图里有一个很实用的提醒：

- Spring Boot 3+ 通常要求 `JDK 17` 及以上
- 版本不匹配会直接导致构建失败或启动异常

所以项目初始化时，不要只看代码能不能写，还要先确认：

- 本地 JDK
- IDE 配置的 JDK
- Maven 使用的 JDK
- Spring Boot 版本要求

这一步没对齐，后面很多问题都只是表象。

### 3. jar 和 war 的选择要提前想清楚

打包方式常见有两种：

- `jar`：适合大多数 Spring Boot 独立运行应用
- `war`：适合传统容器部署模式

它不仅影响输出产物，也会影响：

- 部署方式
- 依赖配置
- 运行方式

如果目标是快速搭建和本地运行，默认优先 `jar` 就够了。

## 四、分层设计决定后续项目是否好维护

后端应用不应该是一堆 Controller 和 Mapper 拼出来的代码仓库，而应该是可维护的分层系统。

一个更合理的基本结构通常包括：

- `controller`：处理请求入口与参数接收
- `service`：承接业务逻辑
- `mapper` / `dao`：负责数据库访问
- `entity` / `model`：承载领域数据
- `config`：管理框架配置

如果再结合前后端分离和领域层演进，可以进一步理解为：

- 表现层负责接口暴露
- 应用层负责流程编排
- 领域层负责复杂业务规则
- 持久层负责数据读写

即使是练习项目，也应该尽量保持这个边界。  
因为后续需求一复杂，没有分层的项目几乎一定会迅速失控。

## 五、REST 控制器是“项目能跑起来”的第一个验证点

课程里用一个很简单的接口说明了 REST 控制器的最小落地方式，这部分很适合作为后端应用搭建后的第一步自测。

### 1. `@RestController` 的含义

`@RestController` 可以理解为：

- `@Controller + @ResponseBody`

它表示这个类主要用于返回接口响应体，而不是渲染页面模板。

### 2. 最小可运行接口

一个最简单的验证接口通常包含：

- 使用 `@RestController` 标记类
- 使用 `@RequestMapping("/test")` 指定路径
- 返回一个简单字符串或 JSON

示例：

```java
@RestController
public class HelloController {

    @RequestMapping("/test")
    public String test() {
        return "hello world";
    }
}
```

### 3. 最小验证方式

完成后可以通过下面的方式检查项目是否真正跑通：

- 启动应用
- 浏览器访问 `http://localhost:8080/test`
- 观察是否能拿到预期响应

这一步的意义不是“功能完成”，而是确认：

- 项目结构没问题
- Spring Boot 能启动
- MVC 能接住请求
- 本地运行链路已建立

## 六、启动失败时，先看依赖和配置是否匹配

课程里有一个非常典型的问题：**Spring Boot 启动失败，原因是数据库配置缺失。**

### 1. 常见现象

典型表现包括：

- 应用上下文初始化异常
- 启动阶段直接失败

### 2. 触发条件

常见原因是：

- 引入了数据访问相关依赖（如 JDBC / JPA）
- 但没有提供数据库连接配置

这类问题本质上不是代码错，而是 **自动装配触发了，但配置没跟上**。

### 3. 处理方式

最实用的处理思路有两个：

- 如果当前不需要数据库功能：移除相关依赖
- 如果需要数据库功能：补齐 `datasource` 配置

示例配置：

```properties
spring.datasource.url=jdbc:mysql://localhost:3306/db_name
spring.datasource.username=root
spring.datasource.password=your_password
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver
```

这个问题很常见，也非常适合用来帮助建立一个意识：

> Spring Boot 的很多“启动报错”，本质上都是依赖、自动装配和配置三者没有对齐。

## 七、开发效率工具的价值，在于减少上下文切换

这份笔记后半段还提到几个辅助插件，它们虽然不是“后端应用搭建”的主干，但很适合作为工程效率补充。

### 1. Translation：帮助阅读英文注释与 API 文档

适用价值：

- 辅助阅读 Spring 等开源框架源码
- 实时翻译英文注释和文档
- 降低源码阅读门槛

如果你正在补基础、读框架源码，这类插件确实有帮助。

### 2. CodeFuse：辅助代码生成、理解与文档补全

笔记里强调的能力包括：

- 根据注释生成代码逻辑
- 解释已有代码功能
- 自动补充方法注释
- 支持生成单元测试

这类工具更适合做“提效”，不适合代替基本功。  
正确用法应该是：

- 用它减少重复劳动
- 用它补充说明和样板
- 但核心逻辑和设计判断仍由人负责

### 3. MyBatisX：提升 Mapper 与 XML 间的跳转效率

它的价值很明确：

- `Mapper 接口 -> XML`
- `XML -> Mapper 接口`
- 减少手动定位 SQL 映射文件的时间

如果项目使用 MyBatis，这属于非常实用的工具型增强。

## 八、把这门课真正学成“会搭项目”的关键

如果只记零散知识点，这份笔记很容易变成：

- 记住了很多术语
- 却不知道怎么串成完整搭建流程

更好的学习顺序应该是：

1. 先理解 Java Web 与 MVC 为什么演进
2. 再理解 SSM 各模块分别负责什么
3. 再理解 Spring Boot 为什么能提升搭建效率
4. 然后完成项目初始化与 JDK / Maven / 打包方式配置
5. 接着写一个最小 REST 控制器验证运行链路
6. 最后学会处理依赖与配置不匹配导致的启动问题

这样你学到的就不是“知识点集合”，而是一条真正能落地的后端应用搭建路径。

## 九、后端应用搭建的复习提纲

如果之后要快速复习，这篇内容可以浓缩成下面几条：

- Java Web 技术栈演进的本质是职责分离
- MVC 解决的是请求处理、业务逻辑和视图职责边界问题
- 前后端分离让后端更聚焦接口与业务
- SSM 的职责分工要清楚：Spring、Spring MVC、MyBatis 各司其职
- Spring Boot 是对 Spring 的封装，核心优势是自动装配、Starter 和独立运行
- 项目初始化时要先确认 Maven 坐标、JDK 版本和打包方式
- 用一个最小 `@RestController` 接口验证项目能否真正跑通
- 启动报错优先检查依赖、自动装配和配置是否一致
- 插件是提效工具，不是替代基础理解的捷径

## 总结

后端应用搭建真正重要的，不是记住某个注解或者某个插件，而是建立一套稳定的理解路径：

- 先知道架构为什么这么设计
- 再知道项目如何初始化
- 再知道接口如何跑起来
- 最后知道问题出现时该从哪里排查

掌握了这条路径，后续无论是继续学数据库接入、ORM、权限体系还是工程化规范，都会顺畅很多。
