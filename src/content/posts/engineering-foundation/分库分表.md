# 分库分表

这份课程笔记的核心非常集中：先说明为什么单库单表会扛不住，再讲分库分表怎么拆、拆哪里、怎么选方案，最后落到 Sharding-JDBC、MyCAT、分布式 ID、事务一致性和跨库查询这些真正会遇到的问题。  
如果按学习逻辑重组，它更适合作为一篇“数据库扩展为什么需要分库分表，以及分完之后怎么把系统稳住”的工程复习文章。

## 一、分库分表到底在解决什么问题

分库分表的本质，是在数据库容量和并发压力上来之后，通过拆分来分散负载。

- `分库`：在表数量不变时，拆分数据库，把请求压力分散到多个库
- `分表`：在库数量不变时，拆分大表，降低单表数据量

它们的共同目标，都是应对高并发、大数据量场景下的数据库瓶颈。  
这也是为什么课程里把它定义为“数据库扩展的基础手段”，而不是随便加一个架构名词。

## 二、为什么不能一上来就分库分表

课程里反复强调一个原则：**只有数据库成为系统瓶颈时，才考虑分库分表。**

更合理的顺序通常是：

1. 先做 SQL 和索引优化
2. 再观察单库单表的承载能力
3. 确认确实被数据库卡住了，再考虑拆分

原因很简单：

- 分库分表会增加系统复杂度
- 维护成本会明显上升
- 查询、事务、路由、统计都会更麻烦

所以它不是“越早上越好”，而是“问题真的到了，才值得上”。

## 三、用食堂打饭来理解分库分表最直观

课程里用食堂窗口的比喻讲演进过程，这个类比很容易记：

- 初始阶段只有一个窗口，对应单库单表
- 员工少的时候效率高，结构简单
- 随着人数增长，单窗口开始排长队，吞吐成为瓶颈
- 增加多个窗口，本质上就是做分散处理

这个类比背后的意思是：

- 系统初期追求简单
- 业务增长后追求扩展
- 扩展能力一旦不足，就要考虑拆分

## 四、分库分表的常见拆法：垂直拆分和水平拆分

### 1. 垂直拆分

垂直拆分是按业务模块或者字段维度拆。

#### 按业务拆分

比如把订单、商品、会员拆成独立数据库：

- 降低耦合
- 业务边界更清晰
- 每个子系统可以独立演进

#### 按字段拆分

比如把高频查询的基础信息和低频的大字段拆开：

- 让常用查询更快
- 提升缓存命中和资源利用率
- 降低单表查询压力

垂直拆分的目标很明确：

- 让单库更专注
- 让单表更轻
- 让资源使用更高效

### 2. 水平拆分

水平拆分是把同一张表的数据分散到多个库或多个表里。

常见做法是基于 `user_id` 等字段取模：

- 数据均匀分布
- 系统负载更平衡
- 更适合大规模数据场景

但水平拆分最重要的不是“能拆”，而是“拆得合不合理”：

- 拆太粗，容易形成热点
- 拆太细，运维和路由复杂度会上升

课程里这部分的核心判断是：  
**水平拆分是分布式数据库架构的基础，但必须平衡扩展性和运维成本。**

## 五、分表怎么拆，范围分片和哈希分片是两种典型思路

### 1. 范围分片

范围分片是按数据区间切分，比如每 `1000w` 条一张表。

优点：

- 支持水平扩容
- 单表大小可控

缺点：

- 容易出现数据倾斜和热点
- 冷数据可能造成资源浪费

### 2. 哈希分片

哈希分片是通过字段取模，把数据均匀分布到多个分片。

优点：

- 能避免热点问题
- 数据分布更均匀

缺点：

- 扩容时可能需要重新 `rehash`
- 历史数据迁移成本高

### 3. 选型时看什么

课程给出的权衡很实用：

- 业务增长是否明显
- 运维成本是否可接受
- 将来是否还要继续扩容

也就是说，分片不是只看当前性能，还要看未来迁移成本。

## 六、分表字段和主键设计，是分库分表成败的关键

### 1. 分表字段怎么选

课程里的原则可以直接记下来：

- **唯一定位**：字段最好能唯一确定目标库表
- **匹配查询**：优先选择高频查询字段，比如商家 ID、用户 ID
- **考虑扩展**：字段选择要兼顾后续增长和维护

选错字段，最常见的后果就是：

- 数据分布混乱
- 查询需要跨库聚合
- 性能变差
- 系统复杂度上升

### 2. 主键为什么不能继续依赖自增

分库分表后，传统数据库自增主键不再适合做全局唯一标识，因为它无法跨库保证唯一性。

课程里推荐的方案是：

- 使用全局唯一 ID
- 常见方案包括 `Snowflake`、`UUID`

其中 `Snowflake` 的特点是：

- `64` 位长整型
- 由时间戳、机器标识、序列号组成
- 支持分布式唯一性
- 还具有一定时间递增趋势，便于索引优化

这也是分库分表里最容易被忽视、但最基础的一环。

## 七、分库分表落地后，最容易暴露的四类问题

### 1. 定位和维护更难

哈希拆分后，数据分布不再直观，排查问题时经常需要额外工具辅助定位。

### 2. 分布式 ID 生成是刚需

一旦不能依赖数据库自增，就必须引入统一的 ID 生成机制。

### 3. 分布式事务复杂度上升

课程里明确提到，这会涉及 `CAP` 和 `BASE` 理解。

也就是说：

- 不能再把事务当成单库事务那样简单处理
- 一致性、可用性、分区容忍性之间需要权衡

### 4. 跨库关联查询和排序很麻烦

跨库 `JOIN` 和排序会严重影响性能。  
课程里给出的常见思路是：

- 将关联字段同步到 `ES`
- 通过搜索引擎做排序和高效分页

这体现的是一个很重要的原则：

**分库分表不是把原来那套 SQL 直接搬过去，而是要一起重构数据访问方式。**

## 八、Sharding-JDBC 和 MyCAT，本质上是两类不同的分片实现思路

课程里专门对比了 `Sharding-JDBC` 和 `MyCAT`，这部分非常适合工程选型时复习。

### 1. 部署模式不同

- `Sharding-JDBC`：客户端模式，`jar` 包集成到应用内
- `MyCAT`：代理模式，独立部署成服务

### 2. 开发侵入性不同

- `Sharding-JDBC` 对 JDBC 兼容的 ORM 框架支持好，比如 `MyBatis`
- 但需要一定代码和配置接入
- `MyCAT` 对应用侵入更小，框架无关
- 但配置相对复杂

### 3. 共同能力

两者都支持：

- 分布式事务
- 读写分离

### 4. 怎么理解这个差异

可以简单概括成一句话：

- 想要“贴近应用、代码内治理”，偏向 `Sharding-JDBC`
- 想要“独立代理、集中治理”，偏向 `MyCAT`

## 九、Sharding-JDBC 的核心配置和验证方式

课程最后把 Sharding-JDBC 的配置与验证讲得很实战，重点可以提炼成三步。

### 1. 配置真实数据源

常见命名方式是：

- `ds0`
- `ds1`
- `ds2`

每个数据源都要配置独立连接信息，比如 URL、用户名、密码。  
它们共同构成分片集群的物理存储节点。

### 2. 配置分片算法

核心逻辑通常是：

- 根据分片字段参与运算
- 通过 `mod` 或类似规则决定数据落点
- 让路由结果精准映射到目标库表

### 3. 配置分片键和主键策略

#### 分片键

分片键要和业务查询条件高度相关，比如用户 ID。

#### 主键策略

课程里再次强调：

- 推荐全局唯一 ID
- 常见实现是 `Snowflake`

### 4. 怎么验证配置正确

课程里给出了很实用的验证思路：

- 插入测试数据，查看 SQL 执行日志
- 根据 ID 余数判断数据分布是否符合预期
- 执行全表查询，验证聚合结果是否完整

这说明分库分表不是“配完就完了”，而是必须通过日志和查询结果来验证路由正确性。

## 十、分库分表真正重要的，不是“拆”，而是“拆完还能查、还能管、还能扩”

如果把这份笔记压缩成一条复习路径，可以记成：

1. 先明确分库分表是为了解决高并发和大数据量瓶颈
2. 只有数据库真的成为瓶颈时才考虑拆分
3. 先理解垂直拆分，再理解水平拆分
4. 再区分范围分片和哈希分片的适用场景
5. 分片字段和主键设计要优先考虑查询、唯一性和扩展性
6. 分库分表后要同步解决分布式 ID、事务、跨库查询和排序问题
7. 最后在 `Sharding-JDBC` 和 `MyCAT` 之间做架构选型
8. 通过 SQL 日志和测试数据验证路由是否正确

## 十一、这门课最核心的工程心法

这份笔记其实在反复传达一个很朴素的结论：

**分库分表不是为了炫技，而是为了在系统规模增长时，把数据库继续稳住。**

拆分只是第一步，真正难的是后面的治理：

- 让路由可控
- 让查询可控
- 让主键可控
- 让事务可控
- 让扩容可控

当这些都被设计进来后，分库分表才算真正从“数据库技巧”变成了“工程能力”。
